Workload axis: echo vs. resize
Same systems, two workloads. echo = no-op (isolates dispatch overhead). resize = real ~ms CPU work (256×256 gradient + half-size nearest-neighbor). Solid bar = echo, translucent = resize. The ranking flips.
apalis ChopFlow Celery

On echo, Celery (1,644/s) beats ChopFlow (1,287/s): Celery's Redis result-backend drain is cheaper than ChopFlow's HTTP submit + stats-poll path, and with no task work that overhead is the whole story. Switch to resize and the ranking flips — apalis (4,175/s) > ChopFlow (1,211/s) > Celery (351/s) at 10k. Once each task does real CPU work, the runtime doing the resize (Rust's image crate for apalis & ChopFlow, Python's Pillow for Celery) dominates over dispatch overhead, and Celery falls to the back. apalis stays ahead of ChopFlow on both axes because its in-process worker + atomic-counter drain carry less per-task overhead than ChopFlow's HTTP-submitted, gRPC-fetched, stats-drained path. Temporal is echo-only here — its durability-per-step model isn't the right tool for a tight resize loop.

Apples, apples, and pears

Celery and apalis are the direct peers: fire-and-forget task queues, just like ChopFlow. Celery is Python+Redis; apalis is Rust+Redis, so it isolates language/runtime with the same broker. Temporal is a different category — a durable workflow engine that persists every workflow step and activity invocation to its database, by design. River sits in between: a durable, transactional Postgres-backed queue that persists per-task state without Temporal's workflow/replay machinery — the "cost of lightweight durability" datapoint. Temporal's lower numbers are a category tax, not a flaw; we include these systems with explicit caveats because showing them is more honest than omitting them.

Why these five, and not more?

Each system earns its slot by sitting in a distinct category: ChopFlow (in-memory, Rust), Celery (Python+Redis), apalis (Rust+Redis), Temporal (durable workflow engine), River (durable lightweight, Postgres). We stopped there. RQ and Dramatiq sit in the same Python/Redis bucket as Celery — Celery is the canonical representative and the others would cluster with it. Sidekiq, Asynq, Hatchet would add a Ruby/Go runtime and a separate broker topology without sharpening the comparison. AWS SQS / RabbitMQ are managed broker services whose numbers reflect cloud network round-trips, not queue-engine overhead, and aren't reproducible on one laptop. If you want to add a system, the contract is one RESULT line — see bench/compare/README.md.

Raw results

The canonical numbers.

Every run completed every task — zero failures across 1,111,000 tasks. Throughput is end-to-end (first submit → last completion); latency is end-to-end wall time per task, sampled by uniform stride, and includes queue wait (the echo handler is near-instant, so most of it is time spent queued).

The 1M run completes with zero failures, but e2e throughput drops to 134/s and tail latency explodes — the single-threaded HTTP submit path can't keep the worker fed as the in-memory store grows to a million entries. The worker drain itself stays fast (post-submit drain > 900k/s). Closing this gap is on the roadmap.

Honest limitations

What these numbers do not tell you.

Read before you quote these numbers
  • The harness polls over HTTP. Drain completion is detected via GET /api/stats (one call per poll, regardless of N); latency is sampled by uniform stride and polled on its own cadence, so figures are upper bounds bounded by the poll interval, not precise per-task durations.
  • Single worker, in-memory storage. No persistence I/O. SQLite-backed durability and multi-worker fan-out will differ — both are worth benchmarking.
  • echo handler does no real work. Throughput is dominated by broker dispatch + ack round-trips, not task execution. The resize workload axis shows how the ranking shifts once each task does real CPU work.
  • 1M is submit-bound. The worker drain scales, but the single-threaded HTTP submit path slows as the in-memory store grows. A batch-submit or multi-producer path would change this — it's on the roadmap.
