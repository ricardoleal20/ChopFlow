Overview

ChopFlow is a durable distributed task queue with a Rust-fast core, multi-language client libraries, and an embedded live operations dashboard — all from a single binary.

What is ChopFlow?#

ChopFlow enqueues, dispatches, and observes background work across a fleet of workers. It belongs to the Celery / Ray / Dask lineage of task queues — not to the workflow-engine family like Temporal or Airflow. ChopFlow does not orchestrate multi-step DAGs or sagas; it reliably executes individual units of background work with retries, dead-lettering, and live observability.

The broker is written in Rust and ships as one binary that embeds the dashboard. Workers pull work from the broker (pull model — backpressure is implicit). Client libraries let you define and enqueue tasks from Rust, Python, or Java.

Workspace crates#

The repository is a Cargo workspace with seven crates:

core

Shared task models, state transitions, and protocol types.

broker

Persistence, scheduling, leases, retries, and APIs (gRPC + HTTP).

worker

Pull-based execution, heartbeats, and acknowledgments.

cli

Local startup, configuration, and operator commands.

demos

Example integrations and usage patterns.

mcp

MCP server exposing the broker as AI-friendly tools, resources, and prompts.

llm-worker

Specialized worker running LLM inference against an OpenAI-compatible endpoint.

Design principles#

  • Durability first. Tasks are persisted before they are eligible for dispatch. A broker restart reconciles in-flight work.
  • Pull-based dispatch. Workers fetch work from the broker; the broker never pushes. Backpressure is implicit.
  • Explicit state. Every task moves through a visible lifecycle. There are no hidden transitions.
  • One binary. The broker embeds the dashboard — no separate frontend deployment to operate.

Not a workflow engine

ChopFlow executes individual tasks. If you need multi-step DAG orchestration, sagas, or long-running workflow state machines, use Temporal or Airflow alongside ChopFlow.

Quickstart

Install ChopFlow, start a broker, register a worker, and enqueue your first task — in under two minutes.

3. Start a worker#

Workers poll the broker, claim matching tasks, and execute them. Tags route work; resources declare capacity.

terminal
$ ./target/release/chopflow_worker start \
    --broker http://localhost:8000 \
    --tags gpu,ml --resources gpu:1,cpu:4

4. Enqueue a task#

Define a task payload in task.json and enqueue it via the CLI. The broker assigns an ID and makes it eligible for dispatch.

terminal
$ ./target/release/chopflow_cli enqueue \

That's it

The task is now in the queue. Open http://localhost:8080 to watch it flow through the lifecycle in the dashboard.

Task Lifecycle

Every task moves through an explicit lifecycle from submission to terminal state. There are no hidden transitions — each state is persisted and visible in the dashboard.

The flow#

A task advances through six stages, driven by the client, the broker, and the worker:

StageActorWhat happens
1. enqueueClientSubmits payload, name, tags, ETA, resource requirements, and retry policy to the broker.
2. QueuedBrokerPersists the task (SQLite). It becomes eligible for dispatch when its ETA arrives.
3. FetchTasksWorkerA worker with matching tags and available resources pulls and atomically claims the task (Queued → Running).
4. RunningWorkerExecutes the handler under a lease. The broker tracks worker ownership.
5. AcknowledgeTaskWorkerReports success (with a result) or a structured failure back to the broker.
6. CompletedBrokerPersists the result and terminal metadata. On failure, the retry policy decides the next transition.

State transitions#

The TaskStatus field on a task encodes its entire lifecycle. The broker never pushes work — workers call FetchTasks and the broker atomically transitions matching Queued tasks to Running. This pull model means backpressure is implicit: if no worker fetches, work simply waits.

On failure, a task with remaining retries transitions back to Queued with an incremented retry count and a computed ETA (see Retry & Dead-Letter). When retries are exhausted, it moves to DeadLettered.

Restart reconcile

On broker startup, any task left Running from a previous run is reset to Queued — its worker is gone after a restart, so the work is requeued rather than lost.

See Task States & Statuses for the full state reference.

Task States & Statuses

ChopFlow tasks move through seven states. Each state is represented by a colored status dot paired with a text label — never color alone.

State reference#

StateDescription
CreatedTask payload submitted to the broker; not yet persisted or eligible for dispatch.
QueuedPersisted in the queue; waiting for a matching worker to claim it.
RunningA worker has claimed the task and is executing it under a lease. The dot pulses while active.
CompletedThe worker acknowledged success; result and terminal metadata are persisted.
FailedThe worker reported failure after exhausting all retry attempts.
DeadLetteredTask moved to the dead-letter store after max retries were exhausted. Available for inspection and replay.
CancelledTask explicitly cancelled by the client before or during execution.

Terminal states

Completed, Failed, DeadLettered, and Cancelled are terminal — a task in any of these states will not transition further unless explicitly replayed.

Scheduling & Recurrence

A Schedule is a recurring or one-shot task template that the broker ticker materializes into Tasks on a background ticker (one tick per second).

Schedule kinds#

KindFieldBehavior
Croncron (5-field)A standard 5-field cron expression (e.g. */2 * * * *, 0 9 * * *). The broker normalizes it to the 6-field form the cron crate expects. Fires on every match.
One-shoteta (RFC3339)Fires once at the given ETA, then self-disables.

Overlap policies#

Each schedule carries an overlap policy that governs what happens when a fire is due but a previous run for the same schedule is still in flight (Queued or Running):

PolicyBehavior
skipSkip this fire and advance next_fire. Default.
coalesceTreated like skip for now; reserved for future merging behavior.
allowMaterialize the task anyway — concurrent runs permitted.

Time semantics#

UTC only

The server evaluates cron and ETAs in UTC. The dashboard converts from the local picker before sending.

Missed cron runs are not backfilled. On broker startup, enabled cron schedules have their next_fire recomputed from now, so the ticker only fires future matches. A disabled one-shot with a past ETA stays disabled until re-enabled.

Task template#

Every schedule carries a TaskTemplate — the name, payload, tags, resources, and max_retries that each materialized task inherits. The dashboard's "Run now" action enqueues a one-off task from the template without disturbing the schedule's overlap accounting.

Manage schedules via the HTTP API or the CLI schedule subcommand.

Retry & Dead-Letter

Failed tasks retry with a configurable backoff strategy and a computed ETA. After the maximum number of retries is exhausted, tasks are dead-lettered.

RetryPolicy#

The RetryPolicy enum (in core/src/retry.rs) defines three strategies:

VariantFieldsBehavior
NoRetry—No retries. A failure transitions straight to Failed/DeadLettered.
Fixeddelay_seconds, max_retriesConstant delay between every retry.
ExponentialBackoffinitial_delay_seconds, max_delay_seconds, max_retries, jitterDelay doubles after each retry, capped at max_delay_seconds. Jitter (0.0–1.0) prevents retry storms.

Defaults#

The exponential_backoff(max_retries) constructor produces a sensible default policy:

core/src/retry.rs
ExponentialBackoff {
    initial_delay_seconds: 5,
    max_delay_seconds: 300,   // 5 minutes
    max_retries,
    jitter: 0.1,
}

Next retry time#

next_retry_time(retry_count) computes when a failed task becomes eligible again. It returns None when the retry count exceeds max_retries — at that point the task transitions to DeadLettered and is available for inspection and replay.

The computed ETA is stored on the task, so a retried task simply sits in Queued until its ETA arrives and a matching worker fetches it.

Dead-letter is terminal

DeadLettered tasks will not retry further on their own. Replay them explicitly from the dashboard or the API.

Priority & Ordering

Every task carries an integer priority. The broker dispatches the highest-priority ready tasks first, so urgent work jumps ahead of a backlog of batch jobs. The default priority is 0, which preserves FIFO ordering.

The priority field#

Task.priority is a signed 32-bit integer (core/src/task.rs). Higher numbers are claimed before lower ones. The default is 0; negative values are allowed and dispatch last. Priority is set at enqueue time and rides along on a schedule's TaskTemplate.

core/src/task.rs
let task = Task::new("resize_image", payload, tags)
    .with_priority(5);

How claim_ready orders#

When a worker fetches tasks, the broker's claim_ready selects ready tasks (matching tags, ETA elapsed, resources satisfied) and orders them by:

TiebreakerDirectionMeaning
priorityDESCHigher priority claimed first.
etaASCWithin a tier, no-ETA (run ASAP) before scheduled.
enqueue_timeASCWithin a tier and ETA, oldest first (FIFO).
idASCFinal deterministic tiebreaker (SQLite).

The same ordering applies to both storage backends. The in-memory backend sorts a candidate scan; SQLite uses ORDER BY priority DESC, eta_ms, enqueue_ms, id backed by a tasks_priority index on (status, priority).

Setting priority#

Priority is accepted everywhere a task is enqueued — the CLI (--priority), the HTTP POST /api/tasks body, the gRPC EnqueueTask request, the MCP enqueue_task tool, and the Java/Python client builders. Omitting it defaults to 0.

FIFO by default

Because the default priority is 0, a fleet of tasks enqueued without a priority still dispatches in enqueue order — priority is strictly opt-in.

SQLite migration#

Existing SQLite databases gain a priority INTEGER NOT NULL DEFAULT 0 column via an idempotent ALTER TABLE on broker startup; old rows default to priority 0. No manual migration step is required.

Resources & Tags

Tags route tasks to matching workers. Resources declare per-worker capacity for CPU, GPU, and memory — the dispatcher only hands a task to a worker that can satisfy it.

Tags#

A task carries a list of tags (e.g. gpu, ml). A worker registers with the tags it can handle. The broker only returns a task to a worker via FetchTasks when the worker's tags match the task's tags. This is how you keep GPU work on GPU workers and CI work on CI workers.

ResourceRequirements#

A task declares the resources it needs as a map of resource name to amount (e.g. {"gpu": 1, "cpu": 4}). The ResourceRequirements type (core/src/resources.rs) is the task-side half of the contract.

core/src/resources.rs
pub struct ResourceRequirements {
    pub resources: HashMap<String, u32>,
}

impl ResourceRequirements {
    pub fn can_be_satisfied_by(&self, availability: &ResourceAvailability) -> bool {
        for (resource, required) in &self.resources {
            match availability.available.get(resource) {
                Some(available) if *required <= *available => continue,
                _ => return false,
            }
        }
        true
    }
}

ResourceAvailability#

A worker declares ResourceAvailability with two maps: total (capacity) and available (currently free). When a worker claims a task, the broker decrements available; when the task is acked, it is returned. This prevents overcommitment — a worker never receives more work than it can run.

Matching, end to end#

When a worker calls FetchTasks, the broker matches queued, ETA-eligible tasks against that worker:

  1. The task's tags must be a subset of the worker's tags.
  2. The task's ResourceRequirements must be satisfiable by the worker's current ResourceAvailability.
  3. The task's ETA must have arrived.

Matching tasks are atomically transitioned Queued → Running and handed to the worker, up to max_tasks.

Core (Rust library)

The chopflow-core crate provides shared task models, state transitions, retry/schedule primitives, and the storage trait used by the broker, worker, and CLI.

Task builder#

Tasks are constructed with a fluent builder:

rust
let task = Task::new("train_model".into(), json!({"lr": 0.001}))

Broker

The chopflow-broker crate is the server: it persists tasks, runs the schedule ticker, manages leases and retries, and serves both gRPC (for workers/CLI) and HTTP/JSON + the embedded dashboard (for browsers).

One shared state#

Both the gRPC service and the HTTP layer read and write a single BrokerState backed by one Storage implementation. The dashboard sees live updates from workers and vice versa — there is no second source of truth.

Ports and protocols#

Port flagDefaultProtocolConsumers
--port8000gRPCWorkers, CLI
--http-port8080HTTP/JSON + embedded UIBrowsers, external tooling

Startup sequence#

  1. Initialize tracing (tracing_subscriber::fmt::init()).
  2. Build the storage backend (SQLite or in-memory).
  3. Reconcile in-flight tasks: any task left Running is reset to Queued.
  4. Construct BrokerState and the ChopFlowBrokerService; spawn the timeout monitor.
  5. Bind the HTTP listener and spawn the Axum server.
  6. Serve gRPC via tonic (blocks until shutdown).

With --open, the broker waits ~300ms for the HTTP listener to bind, then opens the dashboard URL in the platform's default browser.

Flags#

FlagDefaultPurpose
--host127.0.0.1Bind address for both servers.
--port8000gRPC port.
--http-port8080HTTP/dashboard port.
--storagesqlitesqlite or memory.
--db-pathchopflow.dbSQLite database file (sqlite backend only).
--openfalseOpen the dashboard in the default browser on start.

Worker

The chopflow-worker crate is a pull-based executor: it registers with the broker, polls for matching work, runs a handler, and acknowledges the result.

Registration#

On start, the worker calls RegisterWorker with its address, tags, and resource capacity. The broker returns a worker ID used for all subsequent calls.

terminal
$ ./target/release/chopflow_worker start \
    --broker http://localhost:8000 \
    --tags gpu,ml --resources gpu:1,cpu:4

Poll loop#

The worker repeatedly calls FetchTasks with its worker ID and a max_tasks bound. The broker matches queued, ETA-eligible tasks against the worker's tags and available resources, atomically transitions them to Running, and returns them. If no work matches, the worker sleeps for its poll interval and tries again.

Acknowledgment#

After executing a handler, the worker calls AcknowledgeTask with success: true (and a JSON result) or success: false (and an error message). The broker records the outcome and either persists the result or applies the retry policy.

Flags#

FlagDefaultPurpose
-b, --brokerhttp://localhost:8000Broker gRPC address.
-t, --tagsdefaultComma-separated tags this worker handles.
-r, --resourcescpu:1Comma-separated name:amount capacity.
--poll-interval30Seconds between fetch attempts when idle.

Writing a worker

The demo worker (demos crate) is the reference implementation. It registers a handler map keyed by task name; the generic chopflow_worker binary uses the same loop. See Demos.

Embedded Dashboard

The broker embeds a live operations dashboard — no separate frontend deployment required. Serve it from the same binary with --open.

The dashboard is a React + Vite + Tailwind SPA in broker/ui/ (TypeScript, TanStack Query, framer-motion). The built bundle in broker/ui/dist/ is embedded into the broker binary via rust-embed, so a fresh clone runs the UI with no Node toolchain. The HTTP handler serves the SPA from any non-API path, falling back to index.html for client-side routing.

Views#

ViewWhat it shows
OverviewLive cluster stats: queue length, processing, completed, failed, active workers, enabled schedules.
TasksFilterable task ledger with status badges, attempts, timing, and result previews. Click a row for the detail drawer.
WorkersRegistered workers with live resource meters (available vs total CPU/GPU/memory) and liveness.
SchedulesEvery schedule with enable/disable, "run now", next-fire, overlap policy, and delete.

Data freshness#

The SPA polls the HTTP API (see HTTP API Reference) every 2 seconds. There is no separate data plane — the dashboard is a first-class client of the same /api endpoints any external tooling would use, reading the same live BrokerState as the gRPC workers.

Native app

The same React frontend is wrapped as a native macOS app via Tauri 2 (app/src-tauri/). It points at http://127.0.0.1:8080 — nothing is forked or re-implemented.

The desktop app does not run the broker

The Tauri shell is a thin window around the React console — it is a client of the broker, not a host. It does not start the broker, a worker, or any ChopFlow server process. You must start chopflow_broker separately (gRPC :8000, HTTP :8080); the desktop app then connects to it just like a browser tab would.

Demos

LLM Worker

The chopflow-llm-worker crate is a specialized worker that executes LLM inference tasks against an OpenAI-compatible endpoint — turning ChopFlow into an LLM-job orchestrator an agent can drive through the MCP.

It uses the same pull-based protocol as the generic worker (register → heartbeat → FetchTasks → AcknowledgeTask), but with two differences: handlers are async (each inference call is network I/O), and it runs a bounded concurrency pool so a single worker pipelines multiple in-flight requests rather than blocking on one at a time.

Task names#

The worker subscribes to the llm tag by default and dispatches by task name:

Task namePayloadResult
llm.complete{"prompt": "..."}{"text","model","usage"}
llm.chat{"messages": [{"role","content"}]}{"text","model","usage"}

Unknown task names fall back to llm.complete (treating prompt as the input).

Configuration#

Flag / envDefaultPurpose
--brokerhttp://localhost:8000Broker gRPC address.
--tagsllmTags this worker claims.
--concurrency4Max in-flight inference calls (bounded pool).
--api-base / OPENAI_BASE_URLhttps://api.openai.com/v1OpenAI-compatible chat-completions base URL.
--model / LLM_MODELgpt-4o-miniDefault model id.
--api-key / OPENAI_API_KEY—Bearer token. Required.

Run#

terminal
$ OPENAI_API_KEY=sk-... cargo run -p chopflow-llm-worker -- \
    --broker http://localhost:8000 --concurrency 8

With a worker running, an agent (or the CLI) can enqueue an llm.complete task tagged llm; the worker picks it up, calls the model, and acks the result. The MCP run_llm_task tool does this end-to-end and returns the model's text — see run_llm_task.

API key

Never commit an API key. Pass it via the environment or a gitignored .env; the worker reads it from OPENAI_API_KEY if the --api-key flag is omitted.

Rust Client

Rust is the first-class client language. Speak gRPC to the broker with the tonic client generated from proto/proto/chopflow.proto, or embed chopflow-core in-process for tests.

gRPC client#

The proto compiles to a ChopFlowBrokerClient under the chopflow module. This is the same client the worker and CLI use internally:

rust
use chopflow::chop_flow_broker_client::ChopFlowBrokerClient;
use chopflow::{EnqueueTaskRequest, GetTaskStatusRequest};
use tonic::Request;

let mut client = ChopFlowBrokerClient::connect("http://localhost:8000").await?;

let resp = client.enqueue_task(Request::new(EnqueueTaskRequest {
    name: "resize_image".into(),
    payload: r#"{"path":"img.png","w":128}"#.into(),
    tags: vec!["gpu".into()],
    eta: None,
    max_retries: 3,
    resources: HashMap::from[("cpu".into(), 4)],
    priority: 5,
})).await?;

let task_id = resp.into_inner().task_id;
let status = client
    .get_task_status(Request::new(GetTaskStatusRequest { task_id }))
    .await?
    .into_inner()
    .task
    .unwrap()
    .status;

In-process (core)#

For tests or single-process embedding, use chopflow-core directly against an InMemoryStorage — no broker process needed:

rust
use chopflow_core::storage::InMemoryStorage;
use chopflow_core::task::{Task, TaskStatus};

let storage = InMemoryStorage::new();
let mut task = Task::new("echo", serde_json::json!({"msg":"hi"}))
    .with_tags(vec!["demo".into()]);
task.status = TaskStatus::Queued;
storage.insert(task.clone()).await?;

Where the client lives

There is no separate chopflow-client crate today. The gRPC client is generated from the proto by whichever crate needs it (worker, cli, demos). Reuse proto/proto/chopflow.proto to generate it in your own crate.

Python Client

The Python client brings Celery-like ergonomics — a @task decorator, .delay(), and an AsyncResult handle — speaking gRPC to the broker.

Shipped

This client has landed in clients/python. The gRPC contract it speaks is defined in proto/proto/chopflow.proto; see gRPC Reference for the methods it calls.

Ergonomics#

The API surface, mirroring the Celery idiom Python developers already know:

python
from chopflow import task, Client

client = Client("http://localhost:8000")

@task(client, tags=["ml"], resources={"gpu": 1}, max_retries=3)
def train_model(dataset, hyperparams):
    # Your training code here
    return {"accuracy": 0.95}

# Enqueue for asynchronous execution
result = train_model.delay("imagenet", {"lr": 0.001})

# Block until the task reaches a terminal state
output = result.get(timeout=3600)
print(output)  # {"accuracy": 0.95}

Under the hood, .delay() calls EnqueueTask and .get() polls GetTaskStatus until the task is Completed, Failed, or DeadLettered.

gRPC Reference

The broker serves a gRPC API on the configured --port (default 8000) via tonic. This is the wire protocol workers and clients speak; the HTTP API is a thin facade over the same BrokerState.

The service is defined in proto/proto/chopflow.proto (package chopflow). Generate a client in any language with gRPC tooling.

Service methods#

RPCDirectionPurpose
EnqueueTaskclient → brokerSubmit a task (name, JSON payload, tags, ETA, max_retries, resources, priority). Returns task_id.
GetTaskStatusclient → brokerFetch a full Task by ID — status, attempts, result.
CancelTaskclient → brokerCancel a non-terminal task. Returns success.
RegisterWorkerworker → brokerRegister with address, tags, and total resources. Returns worker_id.
WorkerHeartbeatworker → brokerRefresh liveness; optionally update resource availability.
FetchTasksworker → brokerPull up to max_tasks ready tasks matching the worker's tags & resources (Queued → Running). The core of the pull model.
AcknowledgeTaskworker → brokerReport success (with JSON result) or failure (with error). Drives retry / dead-letter.
GetQueueStatsclient → brokerQueue length, processing, completed, failed, active workers.
ListTasksclient → brokerPaginated task list with optional status filter.
ListWorkersclient → brokerAll registered workers.
CreateScheduleclient → brokerCreate a cron or one-shot schedule.
ListSchedulesclient → brokerAll schedules.

Key messages#

Task carries id, name, JSON payload, tags, enqueue_time/eta, retry_count/max_retries, status, a resources map, result (empty until terminal), schedule_id (set when materialized by a schedule), and priority (default 0; higher is claimed first — see Priority & Ordering). TaskStatus is the enum: CREATED=0, QUEUED=1, RUNNING=2, COMPLETED=3, FAILED=4, DEADLETTERED=5, CANCELLED=6.

Pull, don't push

The broker never pushes tasks to workers. A worker calls FetchTasks on its own poll loop, so a slow worker simply stops pulling — backpressure is implicit, no flow-control signaling needed.

MCP Server

A Model Context Protocol server that exposes the ChopFlow broker through all three MCP primitives — tools, resources, and prompts — so an assistant like Claude Desktop, Cursor, or Cherry can enqueue tasks, run LLM jobs, inspect their lifecycle, and manage schedules with no glue code.

The chopflow-mcp crate is a thin wrapper over the broker's HTTP/JSON API. It adds no new broker surface: every tool is a 1:1 wrapper over an HTTP route. The server speaks JSON-RPC over stdio using the official Rust SDK (rmcp); tool input schemas are derived from typed param structs (schemars::JsonSchema), so clients see rich, typed arguments with no manual schema work.

Phase 2 shipped — agent-native

Beyond the Phase 1 control tools, the server now exposes resources (live cluster state an agent can read), prompts (ready-made agent workflows), and two higher-level tools — run_llm_task and wait_for_task. Paired with the chopflow-llm-worker crate, an agent can enqueue an LLM completion and get the answer back synchronously: ChopFlow drives the model. Phase 3 (live notifications) is on the roadmap.

Storage — SQLite

Default storage backend. SQLite in WAL mode for durable persistence with minimal operational overhead.

SqliteStorage holds a single rusqlite connection behind a std::sync::Mutex, with the SQLite library bundled in (no system dependency). All methods are async; synchronous database work is offloaded to tokio::task::spawn_blocking so the runtime is never blocked.

Configuration#

FlagDefaultPurpose
--storagesqliteSelect the backend (sqlite or memory).
--db-pathchopflow.dbPath to the SQLite database file.

Restart reconciliation#

On open, SqliteStorage::reconcile walks every Running task and resets it to Queued. After a broker restart the workers that claimed those tasks are gone, so leaving them Running would orphan them. Re-queuing makes them eligible for the next live worker to claim.

At-least-once

Reconciliation means a task that was mid-flight may execute again after a restart. Design handlers to be idempotent where the side effect matters.

Storage — In-Memory

In-memory storage backend for testing and demos. Not durable — all state is lost on restart.

InMemoryStorage is a HashMap behind a tokio::Mutex. It implements the same Storage trait as SqliteStorage, so it is a drop-in for ephemeral runs. Select it with --storage memory.

terminal
$ ./target/release/chopflow_broker start \
    --storage memory --http-port 8080 --open

Ephemeral

Nothing persists. Stop the broker and every task, worker, and schedule is gone. This is the backend demos/run.sh uses so demo runs start clean.

Because both backends implement the same trait, you can also construct an InMemoryStorage directly in a Rust test to exercise dispatch, retry, and scheduling logic with no I/O — see Rust Client → In-process.

Architecture

ChopFlow is a single-binary system with a pull-based dispatch model, durable persistence, and an embedded dashboard. Seven workspace crates, one shared broker state.

The seven crates#

core

Rust library: Task, Queue, Dispatcher, RetryPolicy, Schedule, Storage, resources. No I/O of its own.

broker

gRPC + HTTP/JSON server, embeds the dashboard UI, owns shared BrokerState.

worker

Pulls work from the broker by tag + resource match, acks results.

cli

chopflow_cli — enqueue, status, schedule management.

demos

Example handlers, demo worker, seed tooling, run scripts.

mcp

Optional MCP server (stdio) wrapping the broker's HTTP API for AI assistants. Adds no broker surface.

llm-worker

Specialized async worker running LLM inference against an OpenAI-compatible endpoint, with bounded concurrency.

Shared BrokerState#

The broker holds a single BrokerState — a shared handle to the Storage and the Dispatcher. Both the gRPC service (:8000, for workers and clients) and the HTTP API + dashboard (:8080) read and write the same live state. A task enqueued from the web UI is immediately visible to a gRPC worker's next FetchTasks, and vice versa — no sync step, no separate data plane.

Pull-based dispatch#

The broker never pushes tasks. A worker calls FetchTasks on its own poll loop; the broker atomically claims matching ready tasks (Queued → Running). A slow or saturated worker simply stops pulling, so backpressure is implicit — there is no flow-control signaling to implement or misconfigure.

Why one binary#

The broker, the dashboard, and the HTTP API ship in a single binary so an operator deploys one process and gets a live, observable cluster. The dashboard is embedded via rust-embed (no separate frontend host); storage defaults to a local SQLite file (no external database to provision). Workers and the CLI are separate binaries that talk to the broker over gRPC.

Category

ChopFlow is a task queue (Celery / Ray / Dask lineage), not a workflow engine. It moves independent units of work through an observable lifecycle across a worker fleet — it does not orchestrate multi-step sagas or long-running workflows the way Temporal does.

FAQ

Frequently asked questions about ChopFlow — the system, the model, and where it fits.

What language is ChopFlow written in, and what can talk to it?#

The core broker and workers are written in Rust (2021 edition). Rust is the first-class client language; Python and Java clients are also available. Workers and the CLI speak gRPC to the broker; browsers and external tooling speak HTTP/JSON against the same live BrokerState.

How does ChopFlow survive a broker restart?#

Tasks persist in SQLite (or the in-memory backend for tests). On boot the broker reconciles in-flight work: any task left Running from a previous run is reset to Queued, since its worker is gone. No silently dropped work — see Storage — SQLite → Restart reconciliation.

Do I need to deploy a separate frontend?#

No. The dashboard is embedded in the broker binary via rust-embed and served on the HTTP port — one process, no Node build required to run, no separate deploy. The same UI also ships as a native macOS app through Tauri.

What happens when a task fails or times out?#

Workers acknowledge each task with a success or structured failure. Failed tasks follow a configurable RetryPolicy (fixed or exponential backoff). Tasks that exhaust their retries are DeadLettered so they stay visible instead of vanishing — see Retry & Dead-Letter.

Can I route work to specific workers?#

Yes. Tasks carry tags and resource requirements; workers register with tags (e.g. gpu,ml) and capacity (CPU, GPU, memory). The dispatcher only hands a task to a worker whose tags match and whose resources are available — see Resources & Tags.

How is this different from Temporal?#

Different category. Temporal is a durable workflow engine — it orchestrates long-running, multi-step processes via event-sourced replay. ChopFlow is a task queue in the Celery / Ray / Dask lineage: discrete units of work, a pull-based dispatch model, leases, retries, and dead-lettering. If you're scheduling background jobs across a worker fleet and observing them live, that's ChopFlow's shape; if you need saga-style workflows with checkpointed replay, Temporal is the right tool.

Is ChopFlow production-ready or research-only?#

Both. It's built for production applications and for distributed-systems research. The experiment directory (reproducible configs and analysis scripts) is planned but not yet landed; the demos crate is the current way to exercise the system end-to-end.

Are missed cron runs backfilled?#

No. On startup, enabled cron schedules have next_fire recomputed from now, so the ticker only fires future matches. A disabled one-shot with a past ETA stays disabled until re-enabled. See Scheduling & Recurrence.

Why pull-based dispatch?#

The broker never pushes tasks. A worker calls FetchTasks on its own poll loop, so a slow or saturated worker simply stops pulling — backpressure is implicit, with no flow-control signaling to implement or misconfigure.
