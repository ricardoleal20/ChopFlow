01 / QUEUE

Task Queue Management

Enqueue and dequeue tasks with metadata, tags, and ETAs.

02 / DISPATCH

Worker Dispatch

Assign tasks to workers by tag and resource availability. Pull model: workers fetch work, the broker never pushes — backpressure is implicit.

03 / RECOVERY

Acknowledgments & Retries

Workers ack success or failure; failures retry with exponential backoff and a computed ETA, then dead-letter.

04 / RESOURCES

Resource Tracking

CPU, GPU, and memory allocation and live utilization per worker.

05 / CLIENTS

Multi-language Interface

Client libraries for Rust, Python, and Java — Celery-like @task and AsyncResult on the Python side.

from chopflow import task, Client

@task(tags=["ml"], resources={"gpu": 1}, ack_late=True)
def train_model(dataset, hyperparams):
    return {"accuracy": 0.95}

result = train_model.delay("imagenet", {"lr": 0.001})
output = result.get(timeout=3600, propagate=False)

use chopflow::{task, Client};

#[task(tags = ["ml"], resources = {"gpu": 1})]
async fn train_model(dataset: &str, hyperparams: Hyperparams) -> Result<Accuracy> {
    Ok(Accuracy { value: 0.95 })
}

let result = train_model.delay("imagenet", &hyperparams);
let output = result.get().await?;

FAQ

Questions, answered.

The practical details before you run ChopFlow in production.

What language is ChopFlow written in, and what can talk to it?
The core broker and workers are written in Rust (2021 edition). Client libraries are available for Rust, Python, and Java, with a Celery-like @task decorator and AsyncResult for Python. Workers and the CLI speak gRPC to the broker; browsers and external tooling speak HTTP/JSON.
How does ChopFlow survive a broker restart?
Tasks persist in SQLite (or an in-memory backend for testing). On boot the broker reconciles in-flight work: any task left Running from a previous run is reset to Queued, since its worker is gone. No silently dropped work.
Do I need to deploy a separate frontend?
No. The dashboard is embedded in the broker binary via rust-embed and served on the HTTP port — one process, no Node build, no separate deploy. The same UI also ships as a native macOS app through Tauri.
What happens when a task fails or times out?
Workers acknowledge each task with a success or structured failure. Failed tasks follow configurable retry policies, and a timeout monitor reclaims work whose lease has expired. Tasks that exhaust retries are dead-lettered so they stay visible instead of vanishing.
Can I route work to specific workers?
Yes. Tasks carry tags and resource requirements; workers register with tags (e.g. gpu,ml) and capacity (CPU, GPU, memory). The dispatcher only hands a task to a worker whose tags match and whose resources are available.
How is this different from Temporal?
Different category. Temporal is a durable workflow engine — it orchestrates long-running, multi-step processes via event-sourced replay. ChopFlow is a task queue in the Celery / Ray / Dask lineage: discrete units of work, a pull-based dispatch model, leases, retries, and dead-lettering. If you're scheduling background jobs across a worker fleet and observing them live, that's ChopFlow's shape; if you need saga-style workflows with checkpointed replay, Temporal is the right tool.
Is ChopFlow production-ready or research-only?
Both. It's built for production applications and for distributed-systems research: the experiment directory ships reproducible configs and analysis scripts. See the GitHub repo for current status and the roadmap.
